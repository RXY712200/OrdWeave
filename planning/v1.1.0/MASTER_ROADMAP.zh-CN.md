## 2. 总体设计原则

1. 全面升级，不是简单修改 gitlink。所有旧功能、LKS 调用路径、适配层、容器组合、资源生命周期和数据库模块都须重新评估。已有实现不是免审理由。
2. 优先直接使用 LKS 公开成熟能力，次选公开 API 组合，数据库自行实现仅在业务契约或证据确有需要时采用。不因追求 API 使用率而强行引入不适合的功能。
3. Full 4.2 延续冻结的 V4 公开接口（64 个函数、14 个公开类型），并非新的 API 世代；使用方式合理且经审查的调用可以保留。生产依赖统一 4.2，不混用 4.1。
4. OrdWeave 的核心业务是永久身份、共享 Record、Collection 顺序及 Occurrence 重复关联、查询、原子修改、持久化、恢复、历史、保留及备份。LKS 管理顺序和有序结构，不承担数据库事务或磁盘耐久性。
5. 正确性优先于速度；性能改善需要代表性实验，拒绝用弱化语义、持久性或验证制造收益。保留负面结果。
6. 不修改上游，不调用私有符号，不移动旧 tag/release，不将任务/证据分支混入生产。阶段之间需要独立审核与进一步授权。

### 2.1 保护的契约

保留现有 44 API 的签名、状态值及既有行为、调用者串行访问、结果所有权、永久类型化 ID 与单调高水位、每次成功非 no-op 修改一个 Revision、引用计数和对象关联；运行时 LKS handle 不等于永久 ID。

保持 Windows x64 C17 静态嵌入式数据库定位。保持 WAL/manifest/segment/frame v3、checkpoint/selection/recovery-root/policy v1、LKS4SNP1。默认以 1.0 与 1.1 双向磁盘兼容为验收要求；如确实需要改变格式或契约，须单独提出并获批准，不在当前路线中默认为允许。

保留失败原子性、COMMIT_UNKNOWN 隔离（停止使用、关闭、经验证重新打开）、语义 WAL 审计、必要保留基线、删除前 recovery root 一致性、独立备份验证及现有 flush 耐久性语义。不得宣称物理掉电认证。新增 API 必须有使用场景、设计和单独授权。

## 3. 为什么升级 Full 4.2

4.2 的实际生产变化集中在显式顺序内部、块标签与局部重标记、移动/删除的局部更新、批量恢复标签初始化以及固定宽度快照编解码。保留块结构与 AVL fallback，标签只是内部顺序加速，不改变永久 ID 或磁盘格式。现有 ManagedOrder 定位接口不因顺序 compare 加速而自动取得同等收益。4.1 已实现的内存布局改进不计作 4.2 新成果。

上游已发布的候选运行时比较（非本项目新测量）显示 4.2 对 4.1 在匹配实验单元的中位耗时约降低 Windows 37.09%、Linux 36.00%，compare-heavy 约降低 80.23%、78.08%。这些不是数据库整体加速率。固定宽度 wire 解码的专门实验以 Preview.1.2 为对照，不能标成直接测得的 4.2/4.1 比较。

既有 OrdWeave Preview.3 生成轨迹研究中，最终运行时候选相对 4.1（匹配轨迹、正式重复中位数、再取匹配比例中位数）的耗时变化：

| 工作 | 耗时降低 |
|---|---:|
| 内存初始化 | 35.18% |
| 内存操作 | 34.67% |
| 持久化初始化 | 3.54% |
| 持久化操作 | 1.15% |
| Checkpoint | 25.18% |
| Reopen | 17.59% |
| History | 18.82% |

持久化存在个别回退，不能保证普遍加速。既有归因约 94.5% 内存操作耗时落在 occurrence staging/publication，约 96.6% 持久化操作耗时落在 WAL 提交（包含 flush，不与子项相加）。均为特定生成轨迹，不是用户真实负载或通用结论。Preview.1 需复核旧证据并补充小规模正式 Stable 对照，而非重跑全部上游矩阵。

## 4. 全面复审矩阵

| LKS 能力 | 当前/潜在数据库用途 | 规划 |
|---|---|---|
| Explicit Order | Collection 成员顺序、插入/移动/删除、比较 | 保留并复审调用组合、局部修改、handle 管理 |
| ManagedOrder | 全局永久 ID 索引；潜在二级字段索引 | 重点研究索引组织与失败边界 |
| Stable Sort | 字段排序、查询结果、批量导入及规范化顺序 | 研究已有重复排序实现及真正需求 |
| Group / GroupBatch | 不可变有序结果、批量排序与归并 | 按实际负载选用；不等于事务 |
| Snapshot | 检查点、原生恢复、历史顺序 | 重点消除数据库层重复构造 |
| Cursor | 遍历、修改检测 | 评估生命周期及调用者契约 |
| LS1 / 路径与 key 辅助 | 历史坐标、跨系统同域排序 | 不作为永久业务 ID；无需使用则明确不适用 |

Preview.1 须根据真实头文件完成 64 函数的紧凑分组清单，记录保留、适配、替换重复实现、研究、不适用和理由。模块覆盖 Record、Collection、Occurrence、Query、LKS adapter、allocation/ownership、Checkpoint、WAL、History、Backup、Retention；所有模块须有结论，而非只研究新增接口。

### 4.1 核心问题和候选技术

**TD-001 全局 Occurrence 索引重建（P0）。** 当前插入/删除逐个重建整个 ManagedOrder 再发布，原子性设计安全但扩展性差，临时内存 O(N)，连续导入/重放可呈现二次或更高成本。移动不重建全局索引。研究四个对照：A 保留现状；B 原地维护（需证明 OOM/Revision cap/跨结构提交，不能假设逆操作必成功）；C 有限 ID 范围分区 ManagedOrder（重点候选，需目录、空分区、稀疏 ID、边界和确定性遍历证明）；D 专用永久 ID 索引（若确有收益，保留 LKS 为 Collection 顺序引擎，证明准备/发布、所有权、确定性遍历）。尚未选型；不可调用私有 bulk builder，ManagedOrder 无公开 reserve/transaction/bulk-build。

**Checkpoint 导入（P1）。** 固定基线 src/checkpoint_core.inc 先经普通 occurrence 插入创建临时 Collection 顺序，随后解码 Snapshot，原生批量恢复并销毁临时顺序。研究直接建立对象和 ID 索引，原生 restore 后完整验证引用、计数、命名空间、每项关联唯一且完整，再发布。不能跳过语义验证，也不能把私有批量构建当作公开接口。

**Record/Query。** 现有字段单链表及等值扫描有小规模优势；比较小型链表、连续/有序数组、适当 LKS 索引及结果排序。未证明成本之前不替换。

**TD-002（P1）。** 同一打开/历史操作重复扫描、独立语义重放和状态构造。研究安全复用已验证结果、减少重复状态及峰值内存；不可让合法 checksum 的坏历史被 checkpoint 掩盖。

**TD-003（P1）。** 完整 checkpoint 缓冲、native snapshot、字段排序及独立状态的峰值内存；研究流式外层 I/O、分段缓冲和减少复制。LKS Snapshot 仍为完整独立对象，不能声称已有流式/增量能力。

**TD-004/005/006（P2）。** 全量备份成本、每次 SHA provider 初始化、未发布临时文件残留。按实测收益和安全性决定；不默认实现增量备份或自动删除未知文件。WAL 逐操作 flush 是现有耐久性保证，不能以取消它获得普通优化收益。

**潜在 correctness 问题（P0）。** src/history_windows.inc 的 ow_history_cleanup 已有 recovery root 时可能在 ow_verify_database 调用 session guard 之前进行重放或 root 协调。尚未确认可达的不合法副作用。Preview.1 复现、确定契约并针对性修复（若确认）；未确认则如实记录。

**EG-001/002。** 物理掉电证据未覆盖，保留限制；增强与实际改动相关的故障、分配、完整性验证。不为清空技术债登记表而强行改动。历史 TD-101/102 的已修复证据保留。

### 4.2 能力扩展候选

二级字段索引、范围和有序查询（高）；稳定排序、批量处理及有序归并（中高）；历史差异和顺序坐标（中）。须证明实际用例、收益、类型/所有权、更新原子性及持久契约。普通批量处理不是原子事务。多操作事务留待独立周期；SQL、网络、跨平台、通用 DBMS 功能竞赛不在本周期。

## 5. 固定执行流程：6 个大阶段，20 个小步骤

小步骤为阶段内部检查点。每阶段一份完整指令、一轮连续实施、一份证据交付、一次独立验收。通过内部步骤即自动继续；普通错误修复、失败重测、审查补充均在原步骤内，不扩增阶段数。阶段边界不自动跨越。以下为批准的总体路线，尚不授权 Preview.2 之后的具体实现。

### Stage 1 — Preview.1（Steps 1–4）依赖升级与架构复审

1. 建立固定对照基线：复用已有轨迹、精简 A/B 基准、预先定义门槛；针对性复现 guard 疑点。
2. 集成准确 Full 4.2 Stable gitlink：检查版本、全部调用、构建、CI pin、兼容性和隔离依赖收益。
3. 全面复审 LKS 64 函数及数据库各模块：形成可追溯能力矩阵和 TD/EG 候选决策清单。
4. 架构筛选与阶段验收：仅必要集成改动与确认的窄修复，确定 Preview.2 候选和门槛建议，不抢跑核心重构。

交付：draft PR、确切 SHA、A/B 原始数据、兼容/guard 证据、完整能力覆盖与架构决策登记、实际测试/CI。门禁：4.2 正确集成，原契约保持，旧格式双向兼容检查，真实测试通过或明确阻塞；不因未批准的候选而扩范围。详细执行以已发出的固定任务文件为准。

### Stage 2 — Preview.2（Steps 5–8）数据库核心与索引优化

5. 永久 ID 索引架构研究：对照 A/B/C/D，关注时间、内存、稀疏 ID、容量边界、确定性遍历、原子性；先确定证据与选择标准。
6. Occurrence 核心重构：实施通过筛选的方案，重点 TD-001，保持永久 ID、引用计数、顺序、Revision/no-op 与失败语义。
7. Record、Collection、Query 核心优化：按证据调整字段、分配、遍历、结果组织和适配方式，复用适合的 Full 4.2 能力。
8. 核心综合验证：比较原版、仅换依赖版及新核心，验证增长趋势、峰值内存和正确性。

门禁：选型有可复现证据，新增复杂度有理由，失败/容量边界得到证明，性能目标在阶段授权时冻结。若无合格替代，保留安全实现并记录未达成目标，不伪造完成。

### Stage 3 — Preview.3（Steps 9–12）持久化、恢复与资源优化

9. Checkpoint 捕获与恢复：充分使用原生 snapshot restore，研究消除临时顺序、重复 staging。
10. 历史及语义重放：减少冗余扫描/状态，保持从 genesis 或必要基线开始的完整审计。
11. WAL、SHA、内存：处理 TD-003/005 候选、编码/复制/摘要生命周期及 I/O，保留耐久性。
12. 备份、保留及恢复收敛：评估 TD-004/006，安全清理、完整备份、故障及持久化兼容。

门禁：损坏历史不被合法 checkpoint 掩盖；root/retention/backup/commit unknown 与既有语义一致；内存及恢复收益经过测量。既有格式与必要 flush 不变，除非另行授权。

### Stage 4 — Preview.4（Steps 13–15）数据库能力升级

13. 索引和查询：研究二级字段索引、范围及有序结果，优先 ManagedOrder 的合适用途。
14. 排序与批量：研究 stable sort、Group、GroupBatch，明确批处理而非事务。
15. 历史能力与功能收敛：Snapshot、LS1、永久 ID 的历史差异等，明确接受/拒绝的功能。

门禁：新增公开 API 和契约须独立批准；无真实价值或安全设计的功能可否决。不要为了完成步骤增加 API。

### Stage 5 — RC.1（Steps 16–18）综合验证与工程收敛

16. 全面正确性与兼容性：全部现有及获准的新 API、ID/Revision、OOM、故障、恶意损坏、checkpoint、history、backup；格式不变则双向兼容。
17. 最终累计性能：A = 1.0+4.1；B = 同一原始生产运行时仅换 4.2；C = 1.1+4.2。隔离依赖收益与数据库自身收益，保留负面结果。
18. 完整技术文档重建：中英文 README、详细 API、实现导读、内部算法/架构、验证地图、格式/兼容、技术债与交接。按实际源码更新文档验证器的版本基线；保留历史 RC/Stable 保护，不删除门禁。

门禁：实际 RC 源码、测试、CI、文档、格式与实验证据一致；明确遗留问题及限制；版本发布材料就绪但不得擅自发布 Stable。

### Stage 6 — Stable（Steps 19–20）发布与独立验收

19. Stable 发布准备：独立审核 RC、集成、准确依赖、最终文档、CI 与发布材料，锁定目标 commit。
20. 获所有者明确授权后正式发布 v1.1.0 Stable：独立核对 annotated tag 的 peeled target、Release 状态、最终源码、资产和发布结果，历史版本不动。

门禁：无未处置的发布阻塞；发布授权、实际远端状态及独立验收三者不可混同。

## 6. 证据和精简验证规则

- 证据优先级：实际固定源码、diff、可重复测试、准确 SHA 的 CI > 当前技术文档 > 讨论/Issue > 旧记录。
- 复用既有有效测试和研究；避免无目的重读、完整重复上游矩阵、每个微小改动重复全部检测、大规模无关日志或过多平台/工具组合。
- 性能：代表性工作负载、小/较大规模、固定种子、必要 warmup、三次测量中位数、原始数据和环境；噪声大或异常时只扩大有关实验。后续阶段依据基线冻结实际阈值。覆盖有意义的时间、资源、分配、I/O、恢复指标，不要求每个步骤测量全部指标。
- 正确性：改动相关的精确断言、容量/OOM/故障覆盖；阶段末采用已有完整 CTest、适用文档校验和准确候选 CI。不关闭已有测试、不削弱语义，不把进程终止测试当成物理掉电保证。
- 阶段报告必须说明实际执行/未执行、数据来源、风险与决定；不要把 Codex 自评当独立验收。
- 任务文件独立分支、固定 commit 链接。开发分支和证据分支分离；实际可审查报告、原始数据和必要日志上传仓库，提供不可变链接。普通阶段内连续实施，不需每步用户回复。真实阻塞、越界变更或所有者工作冲突需停止并说明。
- 每阶段独立审查实际候选源码、范围、测试断言及结果、精确 CI 和证据；PASS 才能申请下一阶段，FAIL 在同阶段修正，BLOCKED 不冒充成功。合并、标签、Release 按阶段明确授权，不自动执行。
