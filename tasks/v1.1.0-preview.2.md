## Step 5 — Permanent-ID index research and selection

TD-001: src/ordweave.c stage_occurrences/publish_occurrences rebuild the entire ManagedOrder on every insert/remove. Moves do not do this. Inspect all occurrence index consumers, including checkpoint export/import, same-state comparison, teardown, queries, history/replay, test instrumentation and handle ownership. Derive current costs and obligations, including capacity/revision exhaustion and sparse high-water IDs.

Compare four alternatives:
A. Current exact Preview.1 as baseline/oracle.
B. In-place ManagedOrder. Reason about commit ordering and all failure paths. Reject naive inverse rollback: removing/reinserting can consume revision capacity and allocate. Do not build an unsafe prototype merely for coverage. If a bounded, public-API-only failure-proof design exists, compare it.
C. Bounded ID-range partitioned ManagedOrder: preferred research candidate, NOT preselected. Stage only affected partition and any needed directory preparation; publication must be non-failing. Consider sparse IDs, empty partitions, ascending traversal and local handle rebinding. Bound both affected partition work and directory growth cost; don't disguise a global directory copy as constant-time mutation.
D. Private permanent-ID index with prepare/commit separation (e.g. sparse radix/page design or another justified structure). Compare maintenance burden, memory, deterministic iteration and allocation-free publication. Preserve LKS for collection ordering, not a new order-maintenance implementation.

Use source/invariant reasoning to prune nonviable alternatives before implementation. Prefer small comparable prototypes of feasible C/D, with a third only if useful. Do not implement four complete production databases. For each candidate, record complexity, ownership, capacity/rollback proof, memory behavior and actual measured results or concrete rejection reason. Keep candidate selection unbiased; choose simplest passing solution. Never use private LKS bulk builder or internal revision fields. No public reserve/transaction/bulk ManagedOrder API exists.

Freeze the compact experiment protocol before new results:
- Same representative archived seed-17 update-heavy traces at N128/2048; one larger bounded scale (suggest N8192 or N16384, choose practical before measurement). Include a separate insertion/removal-heavy scenario to expose TD-001, sparse/deletion gaps and mixed moves/lookups. Use fixed seeds and independent expected order/IDs/ref model. Separate setup/operation timing.
- One warmup, three measured repeats, median, raw data; same machine/compiler, exact source, same trace per pair. Time enough operations to avoid timer noise. Measure resident/temporary requested allocation or comparable peak-memory evidence on selected baseline/candidates; distinguish requested memory from OS RSS, keep diagnostic runs separate. Avoid huge factorial matrices and elaborate tooling.
- Prospective target for chosen core: at least 2x improvement in larger insert/remove workload vs Preview.1, no >10% and >1ms regression in small workload median. Verify no global occurrence-index reconstruction per ordinary mutation and meaningful bounded/sparse resource behavior. Target does not imply all workload classes must double. Any memory increase needs evidence and explicit tradeoff; reject pathological high-water-proportional allocation for sparse IDs. Correctness is mandatory regardless of speed.
- If none qualifies, preserve safe baseline, document negative evidence and report unmet target; do not choose unsafe design or invent a pass. If only a modest improvement is available, report it for independent decision.
