## Stage 1 — Independent harness and capacity

Build reproducible driver(s), deterministic trace format/generator and an independent oracle that uses no LKS code or OrdWeave internal state as ground truth. Use simple C arrays/lists and maps or Python dictionaries/lists for small cases; a scalable independent sequence representation, bulk comparisons or efficiently checked deterministic transformations for large cases. Do not copy LKS block/tag/AVL logic or OrdWeave radix/index algorithms into oracle. Validate oracle with small hand-worked fixtures, deliberately altered expected results and known invalid commands. Generate logical IDs and expected highwaters independently; record actual returned IDs, statuses, Revision and ownership. Include Record values, references, Collection memberships, occurrence identities and order. No reliance on merely comparing hashes from the same subject; full model comparisons at checkpoints, hashes only for receipts/trace identity. Check every operation's relevant result, with small cases full-state each step, large cases sampled comparisons plus predetermined periodic full-state checks and final full comparison. Make these frequencies explicit and affordable before running. Never use a slow oracle to mislabel runtime performance; distinguish DUT and model time where practical.

Capacity ladder (Record/Occurrence/Collection):
- 1k/5k/10; 10k/50k/100; 100k/500k/1000.
- Optional 200k/1m/2000 only after safe measured resource assessment.
- Independent concentrated cases: one Collection with at least 100k live members, optional 500k then 1m; shared Records allowed to isolate Order load. Many tiny independent collections and highly skewed distribution at manageable size. Do not confuse total occurrences with size of one LksOrder.
- Include repeated Record in one Collection and across Collections, mixed empty/nonempty collections, removal/conflict/ref integrity. Check create/populate/order/associations/counts/deletion/teardown; for large states use members arrays and linear comparison rather than quadratic all-pairs checks.
- Cover all six value types via representative fixtures, not giant copies of long payloads. Null versus missing; Bool; signed Int64 extremes; finite binary64 extremes/subnormals/signed zero; UTF-8 multibyte, empty and embedded NUL, byte-prefix strings; binary zero/FF/empty/prefix. Reject invalid UTF-8, nonfinite float, invalid Boolean/bounds according to exact contract. Respect limits and ownership. Report actual peak memory, largest Order and active instances; capacity alone is not reliability proof.

## Stage 2 — Dynamic ordering and structural stress

Prioritize explicit Order use: insertion FRONT/BACK/BEFORE/AFTER, remove, move, compare, members, occurrence_get and genuine no-ops. Generate balanced, read-heavy, modification-heavy, move-heavy traces with explicit ratios recorded. Choose manageable steady live sizes (e.g. 1k–10k) for the bulk of 1m operations distributed over fixed seeds; include a larger active Order targeted case. Ensure sufficient structural mutations rather than mostly reads. Independent model verifies expected status, ID/Revision, association, order, deletion/ref conflicts and no-ops; check local neighborhoods and comparisons per step and periodic full-state. Include sparse permanent IDs after deletions but attribute radix-related faults to OrdWeave unless evidence points elsewhere.

Mandatory focused patterns at reasonable scales:
1. Repeated insertion into one narrow gap (anchor changes and fixed anchor variants), including very hot repeated positions.
2. Occupancy oscillation around block split/merge and relevant minimum/capacity boundaries; derive exact values from pinned LKS source (including 64/32 where applicable), not assume public guarantees. Construct repeated growth/shrink, not just size equals boundary once.
3. Repeated long-distance moves, endpoints and immediate-neighbor no-ops, random reordering; cross-Collection/invalid anchor rejection with unchanged state.
4. Clustered removals followed by refill, repeated empty→nonempty transitions, high ID churn.
5. Create/fill/clear/delete cycles across many Collections; verify shared Record refs, instance independence, repeated lifetime and returned array ownership.
6. Alternating mutations/comparisons, compare signs and transitivity samples against model; no direct reuse of LKS ordering as expected model.

Track actual pattern counts and reached sizes. If feasible lightweight diagnostic counters show real split/merge/relabel/AVL fallback paths, label diagnostic build separately and report which paths actually observed; do not infer a path was hit from workload name or demand every internal branch. Do not patch production to force private invariant changes. Unreached coverage is a limitation.

## Stage 3 — ManagedOrder, equality/range and cache lifecycle

Test Record/Collection ManagedOrder indexes implicitly via public creation/lookup/deletion and explicitly exercise optional field index. Three-way comparison: same independent logical state, index enabled, disabled scan (range uses LKS Stable Sort, not independent), independent oracle without LKS. Use mirrored public DBs or replay deterministic identical states; verify exact IDs and ordering, counts, statuses, ownership, revision. Full equal-bound and genuine nontrivial ranges: unbounded, half-bounded, inclusive/exclusive, inverted, equal-exclusive, empty, broad, narrow, type mismatches; compare unsigned byte spans and strict typed values. Include all-equal values (distinct composite value+ID keys, not actual equal LKS comparator keys), unique, skewed, mixed six-type, absent versus Null, extreme values, embedded NUL and signed-zero ties. For large fixtures (e.g. 8k–100k records as feasible), avoid all-result queries at every step; periodically test full result arrays.

Sustained indexed updates (change type/key, add/remove field, delete Record with no refs, create), unrelated mutations/no-op and rejected edits, replace index name, enable/disable cycles, exact entry/key budgets and one-over boundaries, failure preserves prior valid index, maintenance discards cache AND configuration with no auto rebuild, explicit re-enable. Compare historical range against historical model independently of current cache. Sample returned values/arrays after cache/view/database destruction. Index never persisted/transferred; tests must establish whether it was active using appropriate diagnostic evidence if public outputs cannot distinguish. Do not falsely assert direct LKS equal-key coverage from composite unique rows. Public Stable Sort tie behavior is limited by total value+ID comparator here; state coverage boundaries.

## Stage 4 — Snapshot/persistence/history lifecycle

Use unchanged Windows persistent API and real WAL flush semantics. Never disable flushing for primary evidence. Small fixture (e.g. 32–128 Records, 128–512 Occurrences, several Collections): target 100 checkpoint/close/open/resume cycles with modest mutations per cycle; larger case (e.g. 1k–10k Occurrences, suitable payload size): target 10 cycles. Optional longer campaigns only within budget; report actual cycles and per-cycle operation counts, not a Cartesian product or 1000 giant databases. Include empty orders, single large order, repeated/shared Records, sparse IDs, mixed fields and historical revisions. Use manageable fresh fixtures or supported retention cleanup to bound WAL growth; do not remove files manually to accelerate normal runs. Guard against checkpoint cap.

At each planned cycle check state before/after checkpoint, close/open, independent state and Revision/highwaters, same associations/order/values, continued mutation, history of selected retained revisions (independent logical snapshots/replay), cache absence after reopen. Include Manual/Forever/Last N behavior, actual retention boundary and pruned-view refusal, verification, independently reopenable backup and subsequent independent modifications; ensure backup source untouched. Check snapshots indirectly through real capture/serialize/deserialize/restore in production; direct native API probe only for attribution. Do not require checkpoint bytes to be identical across different generations or identities; compare canonical bytes only under same logical state and matching serialized metadata where meaningful. Preserve fixture/trace metadata, actual IO/cycle counts, and exact discrepancy if failure. No hardware durability claims.

## Stage 6 — Attribution, conclusion, evidence

Review every anomaly. Reproduce deterministically on the exact unchanged subject where possible, minimize trace/fixture while preserving failure, inspect OrdWeave wrapper, object lifetimes, comparators, API preconditions, expected contracts and upstream call path. Use a standalone reproducer using public LKS API with valid comparator, stable owned items and exact Full4.2 pin only when useful to distinguish responsibility. Bound triage to a focused attempt and one meaningful follow-up per important anomaly, preserve unresolved evidence rather than loop. Classify: confirmed LKS defect; confirmed OrdWeave defect; harness/oracle defect (correct and rerun only impacted cells); expected documented limit; environmental/diagnostic issue; unresolved. Do not assign upstream blame just because LKS appears on stack, and do not dismiss unexplained mismatches. State severity, reproducibility, impact, confidence, evidence and minimum repro. If no attributable defect observed, say precisely that; not proven absence. A genuine found bug is useful research, not a requirement to repair/publish. LKS qualification/architecture/paper-baseline decisions remain with owner and upstream reviewer; no direct upstream edits or issue publication.

Publish a single English report, stage coverage matrix (planned/attempted/completed/skipped/failed/partial and why), reproducible source and commands, pinned provenance, frozen protocol, seed/trace manifests, actual counts and resource peaks (define RSS/private bytes/requested allocations), cycle/fault attempts and triggers, independent oracle checks, all adverse results and attribution register. Preserve exact operation trajectories losslessly through deterministic versioned generator+seed+parameters+trace digest and explicit exceptions/receipts; store compressed actual failing/minimized traces and essential original fixture data, and compact raw per-case/checkpoint summaries. For large successful runs, regenerable traces with verified hashes are preferred to huge repetitive Git files; never claim a trace is reproducible if it depends on unrecorded randomness/time or outcomes. Do not upload huge database dumps, secrets, or unnecessary binaries. Record build variants separately. Publish immutable research commit and evidence commit links, actual report and raw inspectable evidence on GitHub, verify remote hashes/refs. Include a short upstream-facing handoff summarizing only LKS-relevant coverage and defects/uncertainties, not inflated OrdWeave-only operations as LKS coverage. Explicitly state untested LKS functions/paths (OrdWeave is not a complete LKS API qualification), no automatic conclusions about unrelated static sort or Mini.

Final self-assessment per stage: COMPLETE (planned bounded checks executed and reported, even if defects discovered), PARTIAL/BLOCKED (missing coverage with reason); separate result per case PASS/FAIL/EXPECTED_LIMIT/NOT_RUN and unresolved attribution. Do not declare a failed case PASS just because research is complete. Independent acceptance remains with ChatGPT/owner. Confirm production paths, gitlink, main, both Stable tag/Release identities and previous branches unchanged; no production modifications, no merge or release. Stop after six stages and evidence delivery. No automatic follow-on research or new version.
