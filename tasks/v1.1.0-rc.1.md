## Step 17 — Cumulative performance (one bounded campaign)

Primary purpose: establish fresh comparable cumulative evidence, not maximize headline ratios or run a separate LKS qualification campaign. Freeze protocol before results. A = exact v1.0.0 Stable runtime with original Full 4.1 pin 70d7f0ef5857b54381b863d292a213909d87459f; B = identical A runtime source/build settings with only LKS pin replaced by Full 4.2 f751e1ee2afd682874281d6dc495969f9eca49eb; C = current RC runtime + same Full 4.2, optional index disabled for common existing APIs. Separate D/within-C enabled-index comparison only for approved new query acceleration; never conflate added feature with common default workload. No changes to historical branches; isolated build trees, not source rewrites. Record source/pin/compiler/host/settings and trace seeds/hashes, independent expected result checks.

Reuse existing archived seed-17 update-heavy traces and drivers where feasible. Small and larger representative sizes (N128 and N2048 suggested; optional single larger memory case only if cheap and informative). Measure setup and mixed insertion/removal/move/query operations in memory; representative persistent mutation, checkpoint, reopen/history (and verify/backup if already in same maintenance driver). Keep fixture setup separate, same trace/state per A/B/C, no large persistent factorial matrix. One warmup and three measured runs, median of per-run metric or total; rotate order if practical, raw rows including negative results. If a baseline becomes impractically slow, bound the common scale before comparing or report the unavailable case with reason; do not extrapolate a ratio or wait on huge quadratic workloads. Avoid timer-floor precision, no compulsory universal speedup.
For the new index use one compact paired C disabled/enabled selective query scenario and one genuinely mixed/interleaved case (choose coprime key stride and bucket count or a deterministic seeded distribution; verify actual bucket occupancy). The prior 1024/17 case with stride17 collapses to one initial bucket: retain it as a low-selectivity result, do not describe it as uniform. The new experiment should fix coverage, not redo Preview.4. Measure build/update/read totals separately, independent expected IDs outside timed spans; report requested memory if available from existing wrappers, distinguish RSS and byte budget. At most one additional nonselective/small case if needed. Reuse accepted resource evidence for unchanged paths.
Present A→B isolated dependency effect, B→C database core effect, A→C cumulative effect on the same matched workload; C off→on index effect separate. No multiplication of previous-stage ratios or claims against unrelated databases. Investigate meaningful unexpected regressions (e.g. >10% and >1ms CPU, >25% and >10ms IO) only on affected scenario with one bounded repeat/inspection; retain noise, limitations and measured tradeoffs. No broad stress/defect-discovery effort beyond this release scope.
