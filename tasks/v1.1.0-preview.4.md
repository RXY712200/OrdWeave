## Step 13 — Secondary index and query capability

Inspect existing live/history ow_query_equal paths and field ownership/mutation/replay/import/exchange/destruction. Current equality uses two scans of Record ManagedOrder and returns increasing permanent Record IDs. Compare that baseline with a modest in-memory, derived secondary field-index prototype using public LKS ManagedOrder (or immutable sorted results for one-shot queries). Explore repeated selective equality and range/ordered lookups on one representative named field; compare build, lookup, update/delete maintenance, requested memory and break-even. Prefer a small bounded prototype over a general query planner. Consider whether an internal change to existing equality actually pays off; implement only if it demonstrably preserves semantics and has a simple failure/lifetime proof. Otherwise retain scanning and report the new capability design as a candidate.
Define comparator and tie rules precisely: type-aware comparisons, no mixed-type coercion, missing distinct from Null, finite binary64 and normalized zeros, byte-length string/binary comparison including embedded NUL, stable permanent-ID tie break. Do not mutate comparator-visible resident keys. ManagedOrder has no public reserve/transaction/bulk construction; do not assume allocating rollback succeeds. Derived index cannot be stale after mutation, WAL replay, import, state exchange or failed commit; no new durable metadata. For a maintained index propose a bounded lifecycle (explicit opt-in if public approval needed), mutation preparation/invalidation, OOM policy, ownership and deterministic output. For a range/ordered query propose minimal typed bounds, missing-value treatment, order/ties, status/output and live/history semantics. No unnecessary general secondary-index subsystem.

Use actual Full 4.2 public header and relevant guides.
